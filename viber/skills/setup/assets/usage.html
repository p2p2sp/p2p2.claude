viber

From an idea to committed code in four steps: understand it, plan it, build it, remember it. Nothing is built before you approve the plan.

Od pomysłu do zacommitowanego kodu w czterech krokach: zrozum, zaplanuj, zbuduj, zapamiętaj. Nic nie powstaje, zanim nie zatwierdzisz planu.

CLAUDE.md

viber knows nothing about your stack. Every agent takes the build and test commands from this project's own instructions, so without them test-runner guesses from whatever manifest it finds, and a task can be committed on a suite that never ran.

viber nic nie wie o twoim stosie technologicznym. Każdy agent bierze polecenia budowania i testów z instrukcji tego projektu, więc bez nich test-runner zgaduje na podstawie manifestu, który akurat znajdzie, a zadanie może zostać zacommitowane na testach, które nigdy się nie uruchomiły.

No CLAUDE.md yet: run /init, then make sure the root file states the exact build command, the exact test command, how to run a single test file, and whatever else a newcomer would get wrong - how to launch the app, the required env, the migrations.

Nie masz jeszcze CLAUDE.md? Uruchom /init, a potem upewnij się, że główny plik podaje dokładne polecenie budowania, dokładne polecenie testów, sposób uruchomienia pojedynczego pliku testów i wszystko inne, co nowa osoba w projekcie zrobiłaby źle: jak uruchomić aplikację, jakich zmiennych środowiskowych potrzeba, jak wykonać migracje.

The ways inPunkty wejścia

/viber:triage
Before any of them: one reported issue (a GitHub number, a link or pasted text) checked against the code, with the next step named - /viber:fixer, /viber:intent or none. It starts nothing itself and posts its report on the issue only when you say so.Przed każdym z nich: jedno zgłoszone issue (numer z GitHuba, link albo wklejony tekst) sprawdzone względem kodu, z nazwanym następnym krokiem: /viber:fixer, /viber:intent albo żaden. Sam niczego nie uruchamia, a raport publikuje na issue tylko wtedy, gdy o to poprosisz.
/viber:intent
An interview about a raw idea, one question at a time. Writes nothing.Wywiad o surowym pomyśle, jedno pytanie naraz. Niczego nie zapisuje.
/viber:fixer
A bug traced to its root cause and proven by a failing test.Błąd prześledzony do przyczyny źródłowej i udowodniony testem, który nie przechodzi.
/viber:prototype
A UI change becomes one working HTML mockup in your project's own look, or three alternatives to choose from - it asks which upfront. You refine it in conversation, then its conclusions go on to /viber:intent, onto the GitHub issue it started from, or both. Mockups land in .temp/viber/prototype/.Zmiana w UI staje się jedną działającą makietą HTML w wyglądzie twojego projektu albo trzema wariantami do wyboru; o to, którą opcję wolisz, pyta na początku. Dopracowujesz ją w rozmowie, a potem wnioski trafiają do /viber:intent, na issue na GitHubie, od którego wszystko się zaczęło, albo w oba miejsca. Makiety lądują w .temp/viber/prototype/.
plan itzaplanuj to
The planner, on what intent or fixer confirmed. Ask for it with neither behind it and the interview starts first.Planista, na podstawie tego, co potwierdził intent albo fixer. Poproś o plan bez żadnego z nich, a najpierw ruszy wywiad.
implement itzaimplementuj to
The orchestrator: task by task, one reviewed commit each.Orkiestrator: zadanie po zadaniu, każde jako jeden zrecenzowany commit.

intent and fixer both end at the planner, prototype ends at intent, and nothing is built before you approve the plan. "plan it" and "implement it" are not commands: anything meaning the same works too.

intent i fixer kończą się na planiście, prototype kończy się na intent, a nic nie powstaje, zanim nie zatwierdzisz planu. „Zaplanuj to” i „zaimplementuj to” nie są komendami: zadziała wszystko, co znaczy to samo, w dowolnym języku.

From a GitHub issueZ issue na GitHubie

With the issues switch on, one issue can carry a change from report to commit:

Przy włączonym przełączniku issues jedno issue może poprowadzić zmianę od zgłoszenia aż do commita:

  1. /viber:triage #42 checks the issue against the code and names the next step./viber:triage #42 sprawdza issue względem kodu i nazywa następny krok.
  2. /viber:intent, /viber:fixer or /viber:prototype, given #42, a link or the bare number, reads that issue instead of you restating it, then keeps working on the same issue. An interview that did not start from one can, once confirmed, save its summary as a new issue built from your project's own issue templates; /viber:intent #42 later resumes it./viber:intent, /viber:fixer albo /viber:prototype z argumentem #42, linkiem lub samym numerem czyta to issue, zamiast kazać ci je streszczać, i dalej pracuje na tym samym issue. Wywiad, który nie zaczął się od issue, może po potwierdzeniu zapisać swoje podsumowanie jako nowe issue, zbudowane z szablonów issue twojego projektu; /viber:intent #42 później go wznawia.
  3. The plan and its specification keep the issue.Plan i jego specyfikacja zachowują powiązanie z issue.
  4. Every commit of the build ends with Refs: #42, so GitHub links each one to the issue once pushed.Każdy commit buildu kończy się linią Refs: #42, więc po wypchnięciu GitHub pokazuje każdy z nich w issue.
T3 - Add the issue creator

Refs: docs/_specs/<run>/plan.md task T3
Refs: #42

A task commit from a run tied to issue #42.Commit zadania z przebiegu powiązanego z issue #42.

/viber:prototype started from an issue can post its conclusions there as a comment. Attach the mockup to that comment yourself in the browser: only the browser accepts an HTML attachment.

/viber:prototype uruchomiony z issue może opublikować tam swoje wnioski jako komentarz. Makietę dołącz do tego komentarza samodzielnie w przeglądarce: tylko przeglądarka przyjmuje załącznik HTML.

After a buildPo buildzie

/viber:e2e needs qawymaga qa
Turns the QA scenarios a build wrote into Playwright tests, run against your own application and committed once they are green. Needs the qa switch to have been on during that build, and it starts off - turn it on before the build, not after.Zamienia scenariusze QA zapisane przez build w testy Playwright, uruchamiane na twojej aplikacji i commitowane, gdy przechodzą. Wymaga, żeby przełącznik qa był włączony podczas tego buildu, a domyślnie jest wyłączony: włącz go przed buildem, nie po nim.

On your own scheduleWe własnym rytmie

/viber:memory
Maps this project's CLAUDE.md cascade, verifies it against the code through a dispatched auditor, and hands what changed to the same writer the build close uses.Mapuje kaskadę CLAUDE.md tego projektu, weryfikuje ją względem kodu przez osobnego agenta audytora i przekazuje zmiany temu samemu autorowi, którego używa zamknięcie buildu.
/viber:rules
Maps .claude/rules/, verifies it the same way, and hands what changed to the same writer the build close uses.Mapuje .claude/rules/, weryfikuje je w ten sam sposób i przekazuje zmiany temu samemu autorowi, którego używa zamknięcie buildu.

Both ask before writing anything and leave the result unstaged, same as the close. Neither needs a build in progress - run them whenever the layer might have drifted.

Oba pytają, zanim cokolwiek zapiszą, i zostawiają wynik poza indeksem gita (unstaged), tak jak zamknięcie buildu. Żaden nie wymaga trwającego buildu: uruchamiaj je, gdy ta warstwa mogła się rozjechać z kodem.

The switchesPrzełączniki .claude/viber.yml

adr onwł.
Decisions worth keeping become the plan's first tasks, under docs/adr/.Decyzje warte zachowania stają się pierwszymi zadaniami planu, w docs/adr/.
memory onwł.
The build closes by updating this project's CLAUDE.md nodes.Build kończy się aktualizacją węzłów CLAUDE.md tego projektu.
rules onwł.
The build closes by updating .claude/rules/.Build kończy się aktualizacją .claude/rules/.
qa offwył.
The build closes by writing its QA scenarios into the run directory.Build kończy się zapisaniem swoich scenariuszy QA w katalogu przebiegu.
cleanup onwł.
The build ends by noting on the specification anything it delivered that the specification does not promise, then archiving the run and dropping the plan, the state file and the trail. They are all in git, which is where the history belongs.Build kończy się odnotowaniem w specyfikacji wszystkiego, co dostarczył, a czego specyfikacja nie obiecuje, potem archiwizuje przebieg i usuwa plan, plik stanu i ślad pracy. Wszystko to zostaje w gicie, bo tam jest miejsce na historię.
plain-plan-review onwł.
A plan written in plain plan mode, without the planner, must pass a review before plan mode can be left.Plan napisany w zwykłym trybie planowania, bez planisty, musi przejść recenzję, zanim będzie można wyjść z trybu planowania.
issues onwł.
intent, fixer and prototype can start from a GitHub issue by number or link, an interview that did not start from one can save its conclusions as a new issue, and a build tied to an issue ends every commit with Refs: #<N>.intent, fixer i prototype mogą zacząć od issue na GitHubie, podanego numerem lub linkiem; wywiad, który nie zaczął się od issue, może zapisać swoje wnioski jako nowe issue, a build powiązany z issue kończy każdy commit linią Refs: #<N>.

Six of the seven start on; qa starts off, because a build that needs acceptance scenarios is the exception rather than the rule. Edit .claude/viber.yml to change that - every key is commented there, and only true counts as on. Turn a switch off with false rather than by deleting it: running /viber:setup again merges in whatever the current version's template carries and your file does not, which is how a new switch reaches a project set up by an older one, and a deleted key is restored at its default by that same merge. Every value you already set survives it.

Sześć z siedmiu jest domyślnie włączonych; qa jest wyłączony, bo build potrzebujący scenariuszy akceptacyjnych to wyjątek, a nie reguła. Zmienisz to w .claude/viber.yml: każdy klucz ma tam komentarz, a za włączony liczy się tylko true. Przełącznik wyłączaj wartością false, a nie przez usunięcie: ponowne uruchomienie /viber:setup dołącza wszystko, co ma szablon bieżącej wersji, a czego brakuje w twoim pliku. Tak nowy przełącznik trafia do projektu skonfigurowanego starszą wersją i tak samo usunięty klucz wraca z wartością domyślną. Każda już ustawiona wartość przetrwa to scalenie.

When your .claude/settings.json already exists, /viber:setup asks whether to merge the recommended permissions into it (fill in what is missing) or reset it to the recommended file from scratch. A reset keeps your old file in .temp/viber/setup/settings.json.bak.

Gdy .claude/settings.json już istnieje, /viber:setup pyta, czy scalić z nim zalecane uprawnienia (uzupełnić braki), czy zresetować go i zapisać zalecany plik od zera. Reset zachowuje stary plik w .temp/viber/setup/settings.json.bak.

DirectoriesKatalogi

runs _specs
Where an open run lives under docs/.Miejsce w docs/, w którym żyje otwarty przebieg.
specifications specs
Where cleanup archives a finished one.Miejsce, w którym cleanup archiwizuje zakończony przebieg.

Both sit in a directories: group and are plain directory names, read only from inside that group - a value carrying a slash is ignored and the default stands.

Oba należą do grupy directories: i są zwykłymi nazwami katalogów, czytanymi tylko z wnętrza tej grupy: wartość zawierająca ukośnik jest ignorowana i obowiązuje domyślna.

TiersPoziomy modeli

min haiku
The cheapest model the build dispatches.Najtańszy model, jaki uruchamia build.
max opus
The strongest one it may reach.Najmocniejszy, po jaki może sięgnąć.

A tiers: group, each value one of haiku, sonnet, opus or fable. Every task, review and retry is kept inside that range; fable runs only when the range names it. An unknown value falls back to its default and an inverted range to the default one. Planning runs on the session's own model and is not bound by it.

Grupa tiers:, każda wartość to jedna z: haiku, sonnet, opus lub fable. Każde zadanie, recenzja i ponowienie mieści się w tym zakresie; fable działa tylko wtedy, gdy zakres go wymienia. Nieznana wartość wraca do domyślnej, a odwrócony zakres do zakresu domyślnego. Planowanie działa na modelu bieżącej sesji i zakres go nie ogranicza.
